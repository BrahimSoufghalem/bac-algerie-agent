# المرحلة 5 — التشغيل والأمان ووصول الوكلاء

## الحدود الصريحة

هذه قدرات تشغيلية وليست شهادة أمن أو دقة تعليمية أو نشرًا على جهاز المستخدم. راجع [أحدث إصلاح واختبار وحدوده](acceptance/grounded-teaching-recovery.md). البيانات الاصطناعية في اختبارات المتصفح ليست منهجًا رسميًا.

## تشغيل وإعادة فتح التطبيق

```bash
cp .env.example .env
# Linux + Docker Engine + Compose v2. أدخل إعدادات التشغيل، لا تحفظ .env في Git.
docker compose up --build -d
docker compose run --rm api python -m bac.cli bootstrap --email owner@example.org
```

افتح `http://127.0.0.1:8090` وسجّل الدخول بحساب المالك. في المرة التالية: `docker compose up -d` وافتح الرابط نفسه. الخدمات تعمل حتى لو أغلقت المتصفح. `docker compose stop` يحفظ volume `library`؛ **لا تستخدم down -v** لأنه يحذف البيانات. تعيد وظائف الاستخراج حالة الطابور المحفوظة، ولا تعيد الصفحات الناجحة؛ تشغيل تدريس مدفوع انقطع يُعلَّم INTERRUPTED دون إعادة تلقائية مدفوعة.

النتائج في volume داخل `/app/data`: `platform.sqlite3` للحسابات/الدردشة/المراجعة، `extraction/state.sqlite3` للاستخراج، `extraction/...` للأصل وصور الصفحات وJSON/crops/Markdown، `snapshots/...` للنشر الثابت، `private/...` للملفات المؤقتة. المدخل API الفعلي هو `uvicorn bac.api.main:create_app --factory --host 127.0.0.1 --port 8090`؛ التشغيل دون Docker يستخدم `DATA_DIR` (افتراضي `./data`). احتفظ بالأصول وبـ **مفتاحي** `.encryption.key`؛ لا تكفي قاعدة البيانات وحدها. بيانات الدردشة ليست مشفّرة end-to-end، والنسخة الاحتياطية تحتوي مفاتيح التشفير والبيانات الخاصة.

## نشر HTTPS

اضبط `DOMAIN` إلى نطاق تملكه و`TLS_EMAIL`، وDNS للخادم، وافتح 80/443 فقط للمستخدمين. ثم:

```bash
docker compose -f compose.yaml -f compose.production.yaml up --build -d
```

Caddy يتولى TLS/HSTS وبث SSE بدون buffering. API على loopback فقط؛ overlay يفرض Secure cookies وTrusted Hosts وPUBLIC_ORIGIN. حافظ على loopback: trust للـ forwarded headers مخصص للـ proxy المحلي الموثوق وليس لبورت API عام. الحاوية غير root، read-only root filesystem، no-new-privileges، cap-drop، tmpfs وmemory/CPU/PID limits. ملفات المستخدم في volume دائم؛ SQLite **خادم Linux واحد فقط** وليس replicas متعددة أو NFS. زد العمال وفق ذاكرة الجهاز/المزود، لا عددًا تعسفيًا؛ برامج الحساب لها حدود إضافية. worker مطلوب للاستخراج/الدردشة/Bريد وتنظيف TTL.

CI يبني الصورة ويفحص Compose/UID/health/401/persistence؛ شهادات TLS والـ DNS وSMTP الحقيقي لا يثبتها CI. Docker غير متاح محليًا. راجع PyMuPDF AGPL/commercial قبل توزيع تجاري. راقب مساحة القرص، audit، errors، outbox، usage؛ لا تعرض tracebacks أو ملفات DB/المفاتيح عبر proxy.

## حسابات وكلمات مرور وبريد

- scrypt + cookie HttpOnly/SameSite Strict + CSRF + origin check. كلمة مرور 12–256 حرفًا.
- لوحة **أمان الحساب** تغير كلمة المرور بمراجعة كلمة المرور الحالية؛ تلغي كل الجلسات/روابط الاستعادة ورموز الوكلاء الخاصة بالمصدر وتوقف التشغيلات الجارية. إلغاء الجلسات متاح مستقلًا.
- SMTP اختياري: `SMTP_HOST/PORT/FROM/USER/PASSWORD`, `PUBLIC_ORIGIN=https://...`. STARTTLS إلزامي، شهادة TLS متحقق منها، timeout 10s. لا fallback لرسائل plaintext. `REQUIRE_VERIFIED_EMAIL=true` اختياري، يتطلب SMTP.
- تسجيل طالب جديد يرسل verification إذا كان البريد مهيأ. recovery والverification بطلب صريح، استجابة عامة لا تكشف وجود البريد، معدلات IP/address، صلاحية20 دقيقة، hash في DB، استخدام واحد transaction-safe. الرابط يحمل fragment؛ تمحوه الواجهة بعد تحميله، ولا يظهر في request URL أو server access log.
- البريد في outbox مشفّر. worker يطالب بlease، 5 محاولات كحد أقصى مع backoff، scrubs secret بعد نجاح/إلغاء/فشل نهائي. `SENT` تعني قبول SMTP وليست وصولًا مؤكّدًا لصندوق المستلم؛ crash بعد الإرسال قد يكرر الرسالة لكن الرابط نفسه one-use. الأخطاء نوع exception فقط، لا SMTP password/link/address.
- إذا لم تُهيأ SMTP تعرض الواجهة ذلك، ولا تدعي إرسال بريد. operator على الخادم يمكنه `python -m bac.cli reset-password --email ...` (getpass لا command line)، أو `verify-email` كتأكيد بشري موثّق في audit. bootstrap يتأكد بالبريد يدويًا باعتباره إجراء مشغّل موثوقًا؛ لا تتحول الحسابات العامة إلى verified تلقائيًا.

## مراجع سرية، لا وكلاء خارجيون

كل طرق `/api/library/*` و`/api/agent/*` تتطلب جلسة المالك؛ الطالب والأستاذ لا يقرآنها حتى بمعرّفات صحيحة. service tokens القديمة مسحوبة وإنشاؤها مرفوض. عامل التدريس يقرأ النسخ المعتمدة داخليًا، ويستطيع فحص pixels دون نشرها في المحادثة. أسماء الأدوات ومدخلاتها ونتائجها والسجلات التقنية لا تُعرض لأي دور؛ درج المحادثة ملخّص مراحل ثابت مُنقّى فقط، لا التفكير الداخلي. `/api/science/*` وOpenAPI غير متاحين في التطبيق العام.

### تحديث النسخة الموجودة بأمان

1. أوقف API وworker وخذ backup كاملًا بـDBs وkeys وPDFs وsnapshots، واحفظه خارج مجلد البيانات ولا تشاركه.
2. حدّث الكود ثم شغّل API وworker من النسخة نفسها. Docker: `docker compose up -d --build api worker` بعد `git pull --ff-only`؛ لا `down -v`.
3. migration006 يضيف origin للملاحظات، يعزل الملاحظات اليدوية القديمة، يسحب المفاتيح الخارجية ويحذف سجلات التدريب الذاتي. العودة للنسخة القديمة تتطلب استعادة النسخة الاحتياطية والكود القديم معًا، لا حذف migration.
4. احفظ مفتاح المزود الحالي في إعداد النماذج على جهازك؛ حفظه في بيئة الاختبار لا يغيّر localhost الخاص بك. لا تضعه في Git أو ملف توثيق.
5. في المسار القديم `MAX_RUN_STEPS` يُتجاهل؛ عند تفعيل منسق المراجع يطبّق `main_max_rounds` سقفًا صغيرًا لطلبات نموذج التدريس (4 افتراضيًا)، مع حجز الجولة الأخيرة للرد. `MAX_RUN_SECONDS=180` افتراضيًا، قابل للضبط حتى 600. تكرار لا يحرز تقدمًا والسياق والحساب والحدود اليومية ما زالت تضبط التشغيل. لا تشغيل مدفوع لا نهائي ولا retries خفية.
6. حدّث الصفحة تحديثًا كاملًا بعد البناء. اختبر سؤالًا عاديًا، تبسيطه، الإيقاف، إعادة فتح المحادثة، عدم وجود مكتبة/صور أصلية/تفاصيل أدوات، وملاحظات القراءة فقط على جهاز النشر الفعلي. تأكد من درج مستقل فوق كل رد وبقاء الدرج السابق بعد السؤال التالي. التحديث الحالي يضيف migration007 لإعدادات نموذج القرار المستقلة ولقطة الإعداد لكل تشغيل؛ migration006 يخص التحديث من نسخة أقدم. لا ترجع إلى كود قديم على قاعدة رُقّيت؛ استعد backup كاملًا مع مفاتيحه وكوده.

تحديث Docker بعد أخذ النسخة الاحتياطية:

```bash
git pull --ff-only
docker compose up -d --build api worker
docker compose ps
```

من مجلد المستودع وبملف Compose ومشروعه و`.env` نفسه؛ تغيير اسم المشروع/volume قد يفتح بيانات فارغة مختلفة. مع النشر الإنتاجي استعمل نفس خيارات `-f` المعتادة. لا تستبدل المفاتيح المحفوظة ولا تحذف volume.

## نسخة احتياطية واستعادة مجرّبة

**أوقف API+worker أولًا**؛ قفل مشترك بعمر العملية، والنسخ يحتاج قفلًا حصريًا. يشمل DBs+keys+originals+rasters+JSON+assets+Markdown+snapshots+private records/files. WAL checkpoint ثم zip + SHA256 لكل ملف + manifest؛ 0600 للملف. ضع النسخة خارج DATA_DIR وانقلها إلى مخزن مشفّر مستقل؛ hashes للتحقق من السلامة، **ليست signature أو إثبات ثقة**.

تشغيل مباشر:

```bash
# أوقف خدماتك/عمليات uvicorn وworker ثم:
python -m bac.cli backup --output /secure-backups/masar-2026-10-01.zip
python -m bac.cli restore --archive /secure-backups/masar-2026-10-01.zip --destination /srv/masar-restored
# destination جديد لا يوجد مسبقًا؛ اضبط DATA_DIR إليه وشغّل migration ثم API+worker.
```

Docker:

```bash
docker compose stop api worker
# /srv/backups يجب أن يكون قابلاً للكتابة لـ UID10001 ومجلدًا خاصًا.
docker compose run --rm --no-deps -v /srv/backups:/backup api python -m bac.cli backup --output /backup/masar.zip
# الاستعادة إلى subdirectory جديد داخل volume آخر، لا الكتابة فوق volume المصدر:
docker volume create masar-restore-stage
docker compose run --rm --no-deps -v /srv/backups:/backup:ro -v masar-restore-stage:/restore api python -m bac.cli restore --archive /backup/masar.zip --destination /restore/new-data
# استخدم المجلد الجديد كـ bind mount لـ /app/data بعد التحقق؛ أبقِ المصدر القديم.
docker compose up -d
```

الاستعادة ترفض destination قائمًا، traversal/absolute/Windows/backslash/duplicates/symlinks/zip bombs ومفاتيح ناقصة/DB تالفة/hash mismatch؛ staging ثم atomic rename. الحدود5GiB uncompressed/100000ملف الافتراضية؛ المكتبات الأكبر تحتاج اختيارًا متعمدًا مثل `--max-restore-gib 50 --max-restore-files 500000`. لا تستعد zip من مصدر غير موثوق ولو صحت hashes. اختبر استعادة شهرية فعلية في staging ولا تحذف آخر نسخة جيدة. الاختبارات أثبتت استعادة login وفك التشفير وكتاب منشور ومصادره والمفتاح الثاني والملف الخاص، لا مجرد فتح zip.

## فحص التحميل والمزود

```bash
python -m bac.ops.load --requests 240 --concurrency 8 --runs 48 --output /tmp/load.json
# منفصل، اختيار صريح وتكلفة فعلية من رصيدك، secrets في env فقط:
python -m bac.ops.evaluate_provider --confirm-cost --image /secure/test-page.png --output /secure/provider-report.json
```

الأول SQLite + ASGI محلي ببيانات مؤقتة وبدون أي API للموديل؛ ليس network/proxy/load benchmark إنتاجيًا. الثاني يحتاج MODEL_API_KEY/BASE_URL/NAME ولا يخمّن نموذجًا؛ لا retry، يعرض schema/bbox/لغة وtool compatibility/مصدر ثابت/رقم بسيط؛ لا يثبت فهم منهج أو حفظ نص كامل أو صحة جواب علمي. يحفظ تقريرًا دون key أو صورة/إجابة كاملة؛ راجع يدويًا مع كتب مرخّصة حقيقية قبل release.

## تشخيص طلب فاشل من Docker دون كشف بيانات خاصة

بعد تحديث API وworker، يستطيع المشغّل الموثوق على الخادم قراءة تقرير آمن لآخر طلب فاشل:

```bash
docker compose exec api python -m bac.cli diagnose-run
# اختياري لطلب محدد تعرف معرّفه داخليًا:
# docker compose exec api python -m bac.cli diagnose-run --run-id RUN_ID
```

مع النشر الإنتاجي استعمل خيارات Compose المعتادة نفسها. هذا أمر محلي للمشغّل، وليس endpoint أو شاشة أو صلاحية للطالب. يطبع حالة التشغيل، عدد الطلبات/الاستدعاءات، رموز فشل من قائمة ثابتة وحقول validation الجذرية وأنواعها فقط؛ لا سؤال أو إجابة نموذج أو arguments أو ملفات/IDs مراجع أو بريد أو API key أو أسماء أدوات خام. التقرير محدود بآخر 40 تشخيصًا، والمعلومات القديمة غير المعروفة تتحول إلى OTHER_FAILURE. الطلبات السابقة لهذا الإصلاح قد لا تملك تشخيص أدوات؛ لا نختلق سببًا لها.

HTTP_503/NETWORK_OR_TIMEOUT/EMPTY_MODEL_RESPONSE تختلف عن schema/REFERENCE_READ_REQUIRED/SCIENTIFIC_TIMEOUT؛ لا تكفي عبارة «تحتاج مراجعة» وحدها لتحديد السبب. يمكن مشاركة **مخرجات هذا الأمر فقط** للفحص، لا raw logs أو قواعد البيانات أو traces. التقرير لا يحتوي سلسلة تفكير النموذج ولا يصدّق الشرح. لا يعيد تنفيذ طلب مدفوع. جرّب السؤال العادي ثم طلب الرسم دون تعليمات أدوات، وراجع بقاء محاولات الدرج وعدم كشف الأصول.

### Google AI Studio / Gemini

للمزوّد الرسمي المتوافق مع OpenAI: Base URL هو `https://generativelanguage.googleapis.com/v1beta/openai/`، واسم النموذج API ID فعلي مثل `gemini-3.5-flash-lite` دون `/` في البداية. توجد مقارنة ضيقة لبادئة `models/` الخاصة بقائمة Google؛ لا تُحذف namespaces من مزوّد آخر. نجاح GET /models أو قراءة metadata لا يثبت توليدًا أو أدوات أو رؤية. لا نبدّل النموذج أو نعيد محاولة مدفوعة تلقائيًا إذا فشل التوليد.

`diagnose-run` يضيف `uses_current_model_config` و`newer_run_exists`: الطلب الفاشل يحتفظ بإعداد النموذج الذي كان نشطًا وقت إدراجه، وليس بالضرورة الإعداد الحالي. لا يطبع IDs إعدادات أو مفاتيح أو أسئلة. ينبغي اختبار طلب جديد بعد الحفظ والتحديث؛ لا تفسّر تقرير آخر طلب فاشل قديم كفشل لإعداد جديد دون المقارنة. راجع [إصلاحات Gemini وحدود القبول](acceptance/gemini-openai-compatibility.md).

إذا نجحت التحية ثم فشل طلب متعدد الاستدعاءات بـHTTP_400، راجع [بروتوكول Gemini والتشخيص الخاص](acceptance/gemini-final-protocol.md). يضيف التقرير المحلي `provider_diagnostics`: HTTP status، تصنيف ثابت `hint` وحالة ثابتة من المزوّد أو UNKNOWN، `forced_final` وأعداد تعريفات/استدعاءات/تواقيع سابقة فقط. التصنيف تلميح وليس سببًا مثبتًا. رسالة الخطأ تُفحص مؤقتًا بحد 16 KiB ولا تُحفظ أو تُعرض؛ النص غير المعروف/الكبير يبقى مجهولًا. تُنقّى البيانات المخزنة مجددًا عند القراءة. هذه الأحداث لا تصل إلى SSE العام أو الدرج أو exports لأي دور؛ الطلبات القديمة لا تكتسب سببًا بأثر رجعي. لا اختبار مدفوع أو retry ضمن هذا الأمر.

أخطاء حجم المصدر/الحزمة الذرية أو عدم إتاحته/صلاحياته/نوعه أصبحت رموزًا ثابتة عند إمكان تحديدها؛ تجاوز حجم feedback يحتفظ بالتشخيص الجذري الخاص أيضًا. لا يعني البحث أو metadata قراءة درس، ولا النجاح البنيوي صحة الشرح. بعد التحديث اختبر محاولة جديدة واحدة بمرجع معتمد يغطي السؤال فعلًا، ثم شارك التقرير المنقّى فقط إن فشلت. لا ترفع الحدود عشوائيًا ولا تتجاوز شرط القراءة.


## إعادة استخراج صفحة واحدة يدويًا (للمالك فقط)

بعد اكتمال المعالجة الأولية، افتح «إدارة المحتوى» ثم اختر النسخة والصفحة المطلوبة من صفحات المصدر أو الحل. زر **إعادة استخراج ص N** يعرض تأكيدًا قبل أي استدعاء جديد؛ فتح المعاينة أو إلغاء التأكيد لا يرسل الصورة للنموذج. يمكن إعادة استخراج صفحة `SUCCESS` أو `NEEDS_REVIEW` أو `FAILED`، وليس فقط الصفحات الفاشلة.

- تُرسل **صورة الصفحة الأصلية نفسها مجددًا** إلى إعداد نموذج **الاستخراج** النشط وقت التأكيد، بمفتاحه المحفوظ. لا يُستخدم نموذج التدريس أو اختيار السياق. يثبت الطلب الإعداد والمفتاح لذلك التشغيل حتى لو تغير الإعداد لاحقًا.
- تتولد مهمة صفحة جديدة بلا نتيجة Vision مخزنة لإعادة الاستخدام؛ لا نعيد بقية الصفحات إلى النموذج. تعاد الفهرسة وبناء الهيكل محليًا بعد النتيجة. سياسة إعادة المحاولة/backoff القائمة ما زالت تنطبق على أخطاء المزود القابلة لإعادة المحاولة؛ مهمة صفحة واحدة ليست ضمانًا لمحاولة HTTP واحدة.
- يتوقف التأكيد أثناء معالجة المصدر بالفعل لمنع المهام المكررة أو التداخل مع بناء الهيكل. يجب أن يكون `worker` شغالًا. تتحدث حالة الصفحة والمعاينة في الواجهة عند انتهاء المهمة؛ لا يعرض النص القديم باعتباره نتيجة جديدة أثناء الانتظار أو الفشل.
- إن كانت النسخة `REVIEWED` أو `PUBLISHED`، تنشئ الواجهة **مسودة نسخة جديدة** أولًا ثم تعيد استخراج الصفحة فيها. تبقى اللقطة المعتمدة والنسخة المفعلة للوكيل ثابتتين حتى مراجعة المسودة وتفعيلها صراحة. إنشاء المسودة وجدولة الصفحة طلبان منفصلان؛ إذا فشلت الجدولة بعد الإنشاء قد تبقى مسودة يمكن إعادة المحاولة منها.
- يلزم تأكيد المراجعة مجددًا. للملفات المرفقة كحل، تعاد مطابقة الحل ومصدره إلى `pending` ويلزم تأكيدها ثانية قبل الاعتماد. تطبق نطاقات الصفحات و`file_id`؛ لا يمكن استخدام زر ملف للوصول لصفحة خارج نطاقه.
- ملفات PDF المتطابقة تشترك في استخراج خام واحد لتجنب التكرار. لهذا تتأثر أيضًا **المسودات غير المعتمدة** التي تستخدم الصفحة الخام نفسها، وتُلغى جاهزية مراجعتها؛ اللقطات المعتمدة والمنشورة لا تتغير.
- هذه الوظيفة للمالك فقط. لا تضيف مكتبة أو وصولًا لصور المراجع للطالب أو الأستاذ. التأكيد ينبه إلى استدعاء جديد قد يستهلك رصيد المزود.

تحديث Docker: خذ نسخة احتياطية وفق القسم أعلاه، ثم `git pull --ff-only` و`docker compose up -d --build api worker`، وأعد تحميل المتصفح تحميلًا كاملًا. لا توجد migration جديدة لهذه الميزة، ولا تحذف volume.

## الطابور بعد انقطاع الاتصال: تشخيص المهام المتبقية

`PENDING` أو `PROCESSING` لا يثبت توقف العامل. إذا بقي `worker` حيًا مع حجوزات سارية، فقد تكون المحاولات تفشل باستمرار دون نتائج جديدة. GET `/models` ناجح يثبت وصول ذلك المسار فقط؛ بعض المزودين يجعلونه عامًا، فلا يثبت قبول المفتاح أو إذن التوليد لطلب POST الصور أو زمن استجابة الاستخراج، ولا يكفي وحده لزيادة المهلة أو تبديل المفاتيح.

بعد هذا التحديث:

```bash
docker compose exec -T worker python -m bac.cli diagnose-extraction
```

التقرير للقراءة فقط: لا يفتح Services/migrations ولا يستدعي المزود ولا يفك تشفير المفاتيح. يعرض أعداد الحالات، العامل الحي، الحد المحفوظ وحد التشغيل الفعلي، اكتمال الصفحات في آخر 10 دقائق، الحجز/انتظار المعدل، مرحلة المهام الجارية وزمنها، وتصنيف آخر خطأ محفوظ لكل مهمة. لا عناوين ملفات/كتب أو معرّفات مصادر/تشغيل أو مستخدمين أو URL/model/key/body. مطابقة الإعداد هنا مقارنة **معرّف الإعداد** فقط، وليست مقارنة المفاتيح؛ `null` يعني عدم توفر معرّف في تشغيل قديم. `last_error_task_counts` أعداد مهام تحمل آخر خطأ، وليست أعداد طلبات أو دليلًا على سبب المهام الجارية.

المراحل الجديدة داخل السجل الخاص: `claimed`, `render`, `rate_wait`, `provider_request`, `response_saved`, `cached_response`, `postprocess`, `structure`. المهام القديمة قد تعرض `unknown_legacy_stage`. لا تُعرض هذه التفاصيل في منصة الطالب أو درج المحادثة.

### ضبط محاولة اختبار محافظة

1. خذ backup كاملًا وفق التعليمات السابقة. إيقاف عامل نشط أو إعادة بنائه قد يلغي طلبًا لم يحفظ الرد بعد؛ قد يكون المزود قبله بالفعل، فلا ضمان لعدم تكرار استهلاكه عند الاستئناف.
2. في `.env` الخاص بالمشروع، ابدأ بتوازي صفحة واحدة. للصفحات التي يحتاج نموذجها زمنًا أطول يمكن اختيار ميزانية طلب أطول صراحة، مثل:

   ```dotenv
   EXTRACTION_WORKERS=1
   REQUEST_TIMEOUT=600
   ```

   هذه قيم اختبار مقترحة، **ليست تغييرًا صامتًا للقيم الافتراضية أو ضمانًا لنجاح Vision**. لا ترفع `MAX_RETRIES` أثناء التشخيص. انخفاض التوازي قد يقلل الحمل؛ لا يصلح رفض المصادقة أو حجب الشبكة أو نموذجًا لا يدعم الصور.
3. حدّث الكود وأعد إنشاء API وworker من الصورة نفسها ومع نفس Compose project/env/volume:

   ```bash
   git pull --ff-only
   docker compose up -d --build api worker
   docker compose exec -T worker python -m bac.cli diagnose-extraction
   ```

4. **`EXTRACTION_WORKERS` صار سقفًا فعليًا للطابور أيضًا**؛ إذا احتفظت قاعدة البيانات بالعدد 8 وأصبح إعداد التشغيل 1، يعرض التقرير `configured_workers:8` و`effective_workers:1`، ولا تحتاج SQL لتعديل العدد. الحجوزات القديمة السارية لا تُسرق أو تُصفّر؛ قد يلزم انتظار انتهاء مهلة الحجز الافتراضية 240 ثانية إذا أُوقفت الحاوية قسرًا.
5. طلب المزود له الآن مهلة إجمالية `REQUEST_TIMEOUT` تشمل DNS وتلقي الاستجابة، بالإضافة إلى مهلات الاتصال (حتى 30 ثانية)، الكتابة (حتى 60)، وانتظار pool (حتى 10). الميزانية الإجمالية تبدأ عند طلب المزود، لا عند انتظار rate/backoff أو render/postprocess. نفس الحارس الإجمالي يحيط بالمزود Native/Custom أيضًا؛ العميل الداخلي قد يفرض مهلة أقل. إعداد `timeout` المحفوظ لنموذج التدريس لا يستبدل `REQUEST_TIMEOUT` للاستخراج المتوافق مع OpenAI.
6. الأخطاء الجديدة تميز `NETWORK_CONNECT_TIMEOUT`, `NETWORK_READ_TIMEOUT`, `NETWORK_WRITE_TIMEOUT`, `NETWORK_POOL_TIMEOUT`, `NETWORK_CONNECT_ERROR`, `NETWORK_READ_ERROR`, `NETWORK_WRITE_ERROR`, `NETWORK_PROTOCOL_ERROR`, `NETWORK_DNS_ERROR`, `NETWORK_REQUEST_DEADLINE`. الخطأ القديم `NETWORK_OR_TIMEOUT` لا يمكن معرفة نوعه بأثر رجعي. المزود native قد يظل يعيد التصنيف العام لأخطاء عميله الداخلي؛ المهلة الإجمالية مستقلة عنه. مراحل السجل وتصنيفات الخطأ أدلة تشخيص، لا إثبات أن المزود لم يقبل الطلب.
7. `SUCCESS` و`NEEDS_REVIEW` لا تُعاد تلقائيًا، والاستجابة المحفوظة للصفحة تُستخدم عند استعادة حجز منتهٍ دون طلب Vision جديد. `FAILED` لا تُصفّر تلقائيًا؛ أعد الفاشلة صراحة من المالك إن أردت محاولتها من جديد. لا تعِد رفع الكتاب أو تعيد استخراج الصفحات الناجحة لمجرد انقطاع الاتصال. لا `down -v` ولا reset عام للحالات/المحاولات.

إذا استمر عدم وجود اكتمالات، أرسل **ناتج diagnose-extraction** بعد مرور ميزانية الطلب المضبوطة، بدل مفاتيح أو محتوى المراجع. يحدد التقرير هل التوقف في طلب المزود أم المعالجة المحلية. لا توجد migration جديدة في هذا الإصلاح؛ تحتاج API وworker من الكود نفسه.
