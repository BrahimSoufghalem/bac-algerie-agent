# حدود وتشخيص استخراج الصور بعد الانقطاع

## الدافع وحدود الاستنتاج

أبلغ المستخدم عن طابور به مهام جاهزة وحجوزات سارية وعامل حي، مع أخطاء عامة `NETWORK_OR_TIMEOUT` متراكمة. فحص metadata GET من عامل المستخدم رجع 200 للإعداد الحالي وإعدادات المعالجة الجارية، وأكد تطابق endpoint/model/protocol/key. ذلك لا يثبت أن طلبات الصور نفسها ناجحة، ولا يحدد نوع الخطأ العام أو زمن التوليد أو رسوم المزود. لم نتصل بحاسوب المستخدم أو نجرب OCR مدفوعًا من هذه البيئة.

## إصلاحات قابلة للتحقق

- سقف عامل التشغيل `EXTRACTION_WORKERS` يُطبّق في worker loop وفي claim العالمي؛ قاعدة بيانات مستعادة بقيمة أكبر لا تتجاهل خفض السقف. لا تعديل قسري للحجوزات السارية.
- مهلة إجمالية لمحاولة Vision تشمل DNS/الاستجابة المتدفقة البطيئة. HTTPX وحده يفرض مهلة لكل عملية قراءة؛ stream متواصل لا يعني انتهاء الطلب. Engine يطبق المهلة الإجمالية على native/custom أيضًا، خارج انتظار المعدل/render/postprocess.
- اتصال/write/pool لا تطول إلى عدة دقائق لمجرد اختيار read/total budget أكبر. مزود OpenAI-compatible يصنف نوع إخفاق الشبكة دون URL/headers/body/key، ولا يضيف retry داخليًا أو fallback مزودًا آخر.
- `RUNNING` بحجز مفقود أو منتهٍ يمكن استعادته مع fencing، مع الحفاظ على الرد المخزن. الحجز الساري لا يُستبدل. حدود retry/backoff السابقة لم تتغير.
- مراحل خاصة محفوظة لكل محاولة، وCLI `diagnose-extraction` يقرأ read-only DB snapshots دون Services initialization/migration/provider/decryption. أعداد الأخطاء حسب المهمة، لا حسب الطلب. لا API جديدة أو تفاصيل تقنية للطالب.

## اختبارات فعلية

النتائج المحلية الفعلية: **281 اختبار خلفية ناجحًا، و22 اختبار متصفح ناجحًا، وRuff select F وTypeScript/Vite ناجحة**. منها 18 حالة جديدة للإصلاح (بما فيها المعلمات)، دون أي طلب Vision مدفوع. اختبارات الإصلاح الجديدة تشمل:

- 8 أصناف إخفاق HTTPX: code محدد، payload خاص لا يظهر، محاولة POST واحدة فقط.
- استجابة ترسل chunks مستمرة تُغلق عند انتهاء المهلة الإجمالية.
- DNS معلق يدخل ضمن الموعد النهائي؛ فشل DNS مصنف دون نص الاستثناء الخاص، بما في ذلك Native Claude. رفض إعداد مهلة غير موجبة أو NaN/Infinity.
- read budget 600 مع connect 30/write 60/pool 10 في خيارات HTTP الفعلية.
- قاعدة تحتفظ بتوازي 8 بينما سقف التشغيل 1: claim واحد عالميًا حتى مع engine آخر؛ stale lease لا ينجح في heartbeat، وباقي المهام تنتهي باستخدام raw cache بلا Vision جديد.
- native/custom fixture معلق يُلغى عند انتهاء المهلة ويُحرر الحجز إلى retry؛ المحاولة التالية تكمل الصفحة فقط.
- CLI لا يستدعي المزود ولا يعدّل صفوف jobs، يعرض مرحلة مزود جارية وحدًا فعليًا 1 مع حد محفوظ 8، ويخفي keys/identities/source IDs/errors الخام.
- DB غير موجودة لا تُنشأ. الحجز المفقود يُستعاد ولا تُمس الحجوزات الحية.
- regression suite يشمل النشر المجمد، إعادة الصفحة المفردة، الحل المطابق، privacy/agent/reference gates وواجهة desktop/mobile.

## ما ليس مثبتًا

لا تدقيق شبكة المزود أو throughput حقيقي أو تجربة OCR مدفوعة جديدة. لا شهادة بأن request_timeout كان سبب إخفاق جهاز المستخدم؛ التصنيف العام القديم فقد التفاصيل اللازمة. نجاح fixtures لا يضمن نجاح الكتاب الحقيقي. تغيير timeout/concurrency اختبار تشغيلي صريح وليس نموذجًا بديلًا أو زيادة غير معلنة للمحاولات. قد يقبل المزود طلبًا انتهت مهلة عميله قبل حفظ الرد؛ لا ضمان بعدم تكرار التكلفة عند retry أو restart.
