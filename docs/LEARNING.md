# Phase 4 — consented learning context, private files, teaching workflows and controls

## A single agent, role-scoped tools

Published retrieval is unchanged: metadata/identity → actual TOC → complete short lesson or stable complete-element parts. Exams and exercise collections remain whole logical bundles, including their supplied/owner-matched solution. Do not put the whole library in the model context. See [RETRIEVAL.md](RETRIEVAL.md).

Students, teachers and owners use the **same AgentEngine, scientific runner and published library**. Public registration creates only students. Only owners assign teachers, roles and limits. A teacher cannot read another student's conversations, private files, notes, scientific results or teaching drafts; owning the platform is not permission for these private API reads either. Database administrators with physical access can inspect server storage: this is authorization separation, not end-to-end encryption.

Teacher tasks: `lesson_plan`, `exercise_set`, `exam`, `grading`, `reference_review`; student-generated `self_practice` is also available. The UI starts an explicit ordinary agent run. `save_teaching_material` saves private generated drafts; `save_practice_test` permits only self-practice. Saved content uses the same source/image/science validation as final answers. Tests require a **separate solution and rubric**; marks sum to `total`; grading requires awarded marks ≤ maximum. Insufficient grading inputs must prompt a question, not invented marks. Generated drafts always have `official=false`, `review_status=draft`; storage is not educational certification. View/export/delete own drafts in the UI. A real provider must support tool calling; automated fixtures prove tool wiring, not the quality/completeness of generated lesson plans or grading.

## Preferences and consented notes

`GET/PUT /api/preferences`: track, up to eight subjects, explanation language (`ar/fr/en`), detail (`brief/balanced/deep`), style (`guided/direct`), `include_approved_notes=false` by default. `PUT /api/conversations/{id}/preferences` accepts only these typed optional overrides; `{}` restores inheritance. Role, system-prompt overrides and budget changes are rejected. Run enqueue snapshots merged preferences and at most six approved notes (≤1000 characters each) transactionally. The constant system prefix + server-authenticated role precedes dynamic **untrusted data**, improving prefix stability without promising a provider cache hit.

`propose_note` creates a **pending** weakness/mistake/mastery/goal suggestion. Its source message and time are assigned by the server from the actual own run; the model cannot select another user's message or approve notes. User review/edit and `consent=true` are required to approve. Explicit manual note creation has the same consent requirement. Suggestions whose source was edited/deleted cannot be silently approved; create a manual note if still appropriate. Notes aren't automatically created from every chat. At most 100 notes and 100 drafts per user; limits refuse new storage rather than silently drop old content.

`GET /api/notes`, `POST /api/notes`, `PUT/DELETE /api/notes/{id}` are own-user only. Including approved notes in future model context requires an additional opt-in in preferences; `list_my_notes` is also opt-in and returns approved notes only. Note approval/edit/deletion or preference changes cancel queued/running user runs to prevent subsequent requests using stale consent/context. Already transmitted data cannot be recalled from the provider. Approved notes are independent of a chat: deleting the chat sets source message to null, but does not silently erase consented learning memory. Delete notes separately or delete the account. Note edit/deletion also scrubs that note from persisted run-context snapshots; already produced chat text/provider copies are not recalled.

## Ephemeral private chat files

`POST /api/conversations/{id}/upload` accepts an actual PDF/image/TXT, not URL fetching. No HTML/SVG/archives. Limits: **10 MB/file, five active files/user, 20 pages/PDF, 24 hours**, images ≤12 million pixels, text UTF-8/no NUL/≤20000 characters. PDFs are inspected and rasterized through the existing resource-limited PyMuPDF subprocess; no OCR/Vision request at upload time. Scanned pages are later delivered as actual multimodal image input to the teaching model, not as a guessed caption or OCR primary source.

`list_private_uploads` lists only own, unexpired files in this chat. `read_private_page` reads a single page: full bounded text, or server-rendered JPEG pixels with a private source ID. Engine caps four images and six MB of JPEG bytes per run, two MB per image; full base64 is **never persisted in DB/SSE/logs** or counted as ordinary text. Normal tool/text context caps still apply. Source/image credit is granted only after bounded data/pixels enter the run context. Private source citation/image paths are server-generated and revalidated when finalizing the answer. A filename/caption alone does not grant visual inspection credit. If the teaching model lacks vision, it must state inability rather than fabricate text.

Own API:
- `GET /api/conversations/{id}/uploads`
- `GET /api/private/{upload_id}/original` (attachment)
- `GET /api/private/{upload_id}/pages/{page}` (raster or text JSON)
- `DELETE /api/private/{upload_id}`

Files are outside shared BookForge storage, published nodes and full-text indexes: `data/private/<opaque-upload-id>/`. There is no automatic publication, cross-user cache or shared search. All reads require ownership, active session and current expiry; API sends `Cache-Control: no-store`. Deletion/expiry cancels affected active chat runs. A worker sweeps every 30 seconds; upload also sweeps expiry. **Reads deny expired content immediately**, even before physical cleanup. If worker/server is off, physical removal waits for restart/next sweep; retain storage securely and monitor it. A process crash may leave partial staging/render files; production orphan sweeps/storage quotas and hostile-parser evaluation remain part of Phase 5. Closing the browser doesn't stop the worker. A file TTL does not erase already-produced chat text or data already sent to a provider.

## Export and deletion

`GET /api/privacy/export` downloads own profile/preferences/notes/drafts/chats and unexpired file metadata; secrets, provider configuration and sessions are excluded. Binary originals must be downloaded separately before expiry. Refuse oversized export (500 chats, bounded message size, 10 MB final JSON) instead of silently truncate. `GET /api/conversations/{id}/export` is an individual chat JSON. UI offers export and password-confirmed account erasure. Account erasure removes chats/runs/scientific results/notes/drafts/usage and private filesystem files. Active runs are cancelled first; retry after they stop. Owner/content-owning or review-attributing accounts need administrative ownership transfer and cannot self-erase via this endpoint. This release does not automate content ownership transfer. Chat deletion cleans its own private files but keeps independently consented notes/drafts; delete them separately.

## Owner controls and actual accounting

`GET/POST /api/owner/accounts`, `PATCH /api/owner/accounts/{id}`: paginated/searchable accounts (50/page), teacher/student creation, role/active state, daily run allowance (rolling 24h; **0 disables**), observed token allowance, messages/minute, concurrent runs, estimated-cost alert. Last active owner cannot be removed. Role/active changes revoke sessions; any changed limits cancel active runs. Audit records previous/new role/limits without passwords/API keys. No user chat/notes/preferences are returned by account administration. Email verification, self-service password recovery and service tokens remain Phase 5.

Account run/token/concurrency limits govern the teaching agent, not a BookForge extraction batch. Extraction retains its own page queue, worker/retry/rate controls; its actual calls still appear in accounting. Do not treat account limits as a global extraction billing cap.

Default one active run per user; transaction-safe admission across chats. Limits check fresh account state, not stale caller data. Message submission and retry are bounded; run retries count toward allowance and are never hidden paid retries. Token allowance is checked **before each new provider request**, using reported input+output tokens from the previous rolling 24h. Missing usage fails closed if a token limit is set. One or more allowed in-flight requests may overshoot before reporting; this is NOT a strict provider billing cap. Daily run and output/context/image/step/time caps provide separate controls. Estimated-cost alert is informational, not an automatic payment ceiling.

`GET /api/usage` is personal. `GET /api/owner/usage?days=30` aggregates actual requests by model/feature and bounded period (1–365 days), token/cache counts, latency, errors, missing usage/cache/cost, run/tool-call counts. Extraction is metered by a wrapper **only when an actual Vision request occurs**; reuse of successful pages/raw JSON/crops/source cache is not billed as a new call. Wrapper keeps vendor files unchanged. Configuration IDs and prices are immutable snapshots; changing UI prices doesn't retroactively recalculate history. Failed attempts are requests too; missing usage remains null. No provider price assumptions or invented token counts.

Prices per million input/output/cached input are owner supplied in the model UI; specify your own billing currency consistently. With usage+input/output prices, missing cache reporting/pricing uses ordinary input price as a labelled upper-price estimate, not an invoice; if required tokens/prices are missing, cost is unavailable. Provider-reported `cached_tokens` is distinct from local immutable-file-cache hit/miss/eviction/bytes metrics. No cross-user answer cache exists. Published-file authorization and current publication are checked before cache lookup; revocation still prevents reads.

`POST /api/owner/models/{agent|extraction}/test` requires `confirm=true` and an explicit click. It performs **GET /models only**, with safe URL validation, no redirect/environment proxy, 10s deadline, 256 KB response cap, three tests/minute. Secrets and provider error bodies aren't returned or logged. It checks reachability/authentication and advertised model identity, NOT vision/tool capability, teaching quality or pricing. Some compatible providers don't implement model listing; a failed listing doesn't prove their chat endpoint is unusable. No implicit paid generation at save/navigation/upload; an actual teaching/extraction run is the cost-incurring action.

## Deployment/verification limits

This is single-host Linux/SQLite/local-disk architecture. Migrations are serialized using a Linux file lock during API/worker startup. Private-file cleanup runs with the worker; persistent TTL file deletion requires the services to run. Back up DB/files/encryption key consistently, protect data directory, use HTTPS/secure cookies before external access. Full native parser audit, quotas/orphan sweep/load testing, privacy retention policy, provider quality testing, backups/restore and production acceptance remain Phase 5. New visual inspection is pending if the image tool is unavailable; functional browser assertions are not a visual approval.
